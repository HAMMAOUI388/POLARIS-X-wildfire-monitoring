2. Open-Meteo API Taxonomy

Open-Meteo offers three distinct endpoint families. Confusing them introduces the wrong data into the model and the wrong timestamps into provenance records. The distinctions below are factual, drawn from the official documentation.

EndpointData typeSource modelsCoverage startBase host
/v1/forecast Operational NWP forecast GFS, ECMWF IFS, ICON, AROME, UKMO, JMA, GEM, … Now − 92 days (via past_days) api.open-meteo.com
/v1/archive Reanalysis (ERA5 / ERA5-Land) and archived NWP analysis (ECMWF IFS) ERA5 (1940–), ERA5-Land (1950–), ECMWF IFS (2017–), CERRA (1985–2021) 1940 for ERA5 archive-api.open-meteo.com
/v1/archive (historical-forecast) Archived NWP forecast runs ECMWF IFS HRES (2017), GFS (2021), HRRR (2018), ICON (2022), UKMO (2022) 2016–2022 depending on model historical-forecast-api.open-meteo.com
⚠

ERA5 / ERA5-Land are not weather-station observations. They are ECMWF reanalysis products — a model that ingests diverse observations (stations, aircraft, satellites, buoys, radar) and produces a physically consistent gridded estimate. ERA5 is ~25 km resolution; ERA5-Land is ~9 km. Values at a specific point are interpolated from the model grid, not read from a local sensor. This must be reflected in provenance records and in any user-facing explanation of data quality.

3. Time Semantics & Provenance Requirements

The existing schema already separates time concepts correctly. Each concept maps to a distinct field and must be populated explicitly — none should be inferred from another.

ConceptDefinitionSchema columnOpen-Meteo source
Valid time The moment or period the value describes weather_forecasts.valid_from / valid_to The time array in every response (always valid time)
Forecast issue (run) time When the NWP model cycle that produced the value was initialised weather_forecasts.issued_at Not directly returned by the seamless APIs; must be inferred from model cycle cadence or obtained from the Single Runs API
Retrieval time When POLARIS X fetched the value Implicit via ingested_at / created_at Record at HTTP response time
ERA5 reference time The centre of the reanalysis analysis window weather_observations.observed_at The time array for archive calls
△

The seamless Forecast API does not expose the model run time. When past_days is used, the returned timeseries blends multiple initialisation cycles into a continuous valid-time series — individual run boundaries are not marked. If the application needs to reason about forecast age from the run time (e.g., "this 12-hour forecast was initialised at 00Z"), it must either query the Single Runs API with an explicit run= parameter, or record the retrieval time and derive a conservative estimate.

Accumulation variables (precipitation, radiation, ET₀) cover the preceding hour, not the instant at the label. valid_from should therefore be set to time − 1 hour and valid_to to time for these variables.

5. Licensing & Commercial Risk

Free tier licence CC-BY 4.0 Non-Commercial restriction

The free API is licensed under CC-BY 4.0 and explicitly restricted to non-commercial use. "Commercial" includes subscriptions, advertising, promotional use, and undisclosed research at commercial entities.

Rate limits: 600 calls/min · 5,000 calls/hr · 10,000 calls/day · 300,000 calls/month. Enforced by IP address; no API key required for the free tier.

⚠

The free tier is not suitable for a commercial POLARIS X deployment. If POLARIS X is ever offered as a commercial product or service — with subscriptions, advertising revenue, or embedded in a commercial offering — the free Open-Meteo tier is contractually prohibited. A paid commercial plan with an apikey and the customer- server prefix is required.

A government or public-institution research deployment (e.g., a NASA-operated non-commercial system) likely qualifies under the "public research at public institutions" exemption in Open-Meteo's terms, but this should be confirmed with Open-Meteo directly before operating at scale.

Attribution requirements multi-layer obligation

CC-BY 4.0 requires crediting Open-Meteo (Zenodo DOI 10.5281/ZENODO.7970649) in any product that uses the data. ERA5 and ERA5-Land carry additional upstream attribution obligations to ECMWF and Copernicus Climate Change Service ("Generated using Copernicus Climate Change Service information").

The current codebase and .env.example contain no attribution variables or configuration for Open-Meteo. These must be added before any data is served to users.

6. Audit Findings

F-01 — No weather ingestion pipeline blocker

The weather_observations and weather_forecasts tables exist but are populated only with synthetic seed fixtures. The assessment engine always returns insufficient_data. No scheduler, HTTP client, or Open-Meteo integration code is present in the repository.

F-02 — issued_at cannot be reliably populated from the seamless Forecast API design gap

The weather_forecasts.issued_at column is present and correct by design, but the Open-Meteo seamless /v1/forecast endpoint stitches multiple model runs into one continuous valid-time series without exposing run initialisation times. Populating issued_at requires either the Single Runs API or a documented approximation policy (e.g., record retrieval time and note that it bounds — but does not equal — issue time).

F-03 — ERA5 / ERA5-Land must not be described as local-station observations accuracy

ERA5 and ERA5-Land are gridded reanalysis products, not weather-station measurements. Any provenance record, API response, or user-facing label that describes these values as "local observations" or "measured" would be scientifically incorrect. The data_sources source_type field and raw_payload must clearly identify the model and resolution.

F-04 — ERA5 data has a 5-day lag freshness constraint

ERA5 and ERA5-Land are updated daily with a 5-day delay. They cannot serve near-real-time weather. For operational wildfire monitoring (hours-to-days lookahead), the /v1/forecast endpoint with past_days is the appropriate source. ERA5 is suitable only for historical context (e.g., antecedent drought conditions, validation datasets).

F-05 — Accumulation variables require adjusted valid_from / valid_to provenance error risk

Open-Meteo labels precipitation, radiation, ET₀, and wind gust variables with the end of their accumulation window. Storing the API time value as both valid_from and the start of the window would misrepresent the period covered. For accumulation variables, valid_from = time − 1h and valid_to = time.

F-06 — Soil moisture depth layers differ between endpoints normalisation required

The Forecast API returns soil moisture at 0–1 cm, 1–3 cm, 3–9 cm, 9–27 cm, 27–81 cm; the ERA5 archive returns 0–7 cm, 7–28 cm, 28–100 cm, 100–255 cm. Blending both into a single feature without labelling the layer definition would produce an inconsistent soil moisture series.

F-07 — Free tier commercial use prohibition not addressed legal risk

The free Open-Meteo API (CC-BY 4.0, non-commercial) must not be used if POLARIS X is deployed commercially. No configuration, documentation, or code in the repository addresses this distinction. Before any deployment, the intended use must be classified and, if commercial, a paid plan with an API key must be configured.

F-08 — No attribution variables in config or .env.example compliance gap

CC-BY 4.0 requires attribution to Open-Meteo (and, for ERA5 data, to ECMWF/Copernicus) in any product. The current config.py and .env.example contain no WEATHER_PROVIDER, OPEN_METEO_API_KEY, or attribution variables.

F-09 — Weather schema design is sound no action needed

The weather_forecasts table separates issued_at, valid_from, and valid_to correctly. The weather_observations table stores observed_at separately from ingested_at. The variables JSONB column accommodates multi-variable payloads. The data_sources foreign key provides provenance. No schema changes are required for Phase 6.

F-10 — Assessment engine provenance contract is compatible no action needed

The assess() function in risk/assessment.py already enforces observed_at + max_age_seconds per feature. A weather ingestion module that populates these provenance fields will integrate without changes to the assessment engine.

7. Implementation Proposal (awaiting approval)

ℹ

This is a proposal only. No files have been modified. Approval is requested before any implementation begins.

1
Add weather configuration to config.py and .env.example

Add OPEN_METEO_API_KEY (empty string default — free tier requires none), OPEN_METEO_FORECAST_URL, OPEN_METEO_ARCHIVE_URL, OPEN_METEO_COMMERCIAL (boolean flag), WEATHER_ATTRIBUTION, and WEATHER_MAX_AGE_FORECAST_SECONDS / WEATHER_MAX_AGE_ERA5_SECONDS. Gate commercial vs. non-commercial paths explicitly on the flag.

2
Create src/polaris_x/integrations/weather.py

A focused HTTP client module (using urllib.request or a lightweight dependency) for the Open-Meteo Forecast API. It fetches hourly wildfire-relevant variables for a given coordinate, normalises the response into a list of dicts keyed by valid time, separates accumulation-variable windows (setting valid_from = time − 1h), and builds a provenance dict with source, model, resolution_km, retrieval_time, and valid_at. No run-time field is populated from the seamless API; retrieval time is documented as the only available bound.

3
Create src/polaris_x/ingestion/weather.py

An ingestion module that calls the weather client and writes to weather_observations (for archive / ERA5 calls) and weather_forecasts (for operational forecast calls), linking to the appropriate data_sources row. ERA5 rows must be typed source_type="reanalysis"; forecast rows source_type="nwp_forecast". The DataSource.metadata_json must record model name, grid resolution, and applicable attribution text.

4
Add an Alembic migration (0005) only if schema changes are needed

Based on the audit, the existing schema requires no structural changes. Migration 0005 would only be created if the Phase 6 implementation reveals a need for a new column or index (e.g., an index on weather_forecasts(valid_from, location_id) for query performance).

5
Add tests with synthetic fixture responses

Unit tests for the weather client using captured (static) JSON responses — no live network calls in CI. Integration test confirming that a normalised weather feature with correct provenance fields passes the assessment engine's freshness check. No real Open-Meteo calls in the test suite.

6
Document licensing and attribution in docs/weather-integration.md

Record the CC-BY 4.0 / non-commercial restriction, the commercial plan requirement, ERA5 Copernicus attribution text, and the soil-layer normalisation policy. This document must be reviewed before any commercial deployment.
